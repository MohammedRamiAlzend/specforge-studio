# PRD — SpecForge Studio

## 1. What SpecForge Studio Is

SpecForge Studio is an **internal software engineering lifecycle platform** that turns visual planning and structured specifications into engineering documentation, diagrams, roadmaps, and executable task packs.

It is a **visual spec engine**: users model requirements, workflows, data, and architecture visually; the system generates the engineering artifacts from that structured data. Users never write Mermaid or hand-maintain Markdown documentation.

It is also a **governance and traceability system**: every artifact has a stable ID, every requirement can be traced to use cases, tasks, tests, and approvals, and every phase of the lifecycle is explicit.

## 2. Who Uses It

Internal engineering teams: product owners, engineering leads, developers, and AI agents.

- Product owners author requirements and approve final scope.
- Engineering leads own architecture, data model, and API contracts.
- Developers execute tasks generated by the system.
- AI agents execute agent-neutral task packs with concrete checklists.
- Governors approve security-sensitive and production decisions.

Full role definitions: `user-roles.md`.

## 3. The Main Problem It Solves

1. **Specs rot.** Requirements live in documents that drift from code, diagrams, and reality.
2. **Traceability is manual.** Nobody knows which requirement produced which task or test.
3. **Diagrams are hand-maintained.** Teams hand-write Mermaid and it goes stale.
4. **Agent work is unstructured.** AI agents are given vague prompts instead of executable, verifiable checklists.
5. **Planning to execution is a cliff.** Roadmaps and task packs are created ad hoc, not generated from the model.
6. **Approval is invisible.** There is no record of who approved what, when, and why.

SpecForge Studio converts a single structured model into docs, diagrams, roadmaps, and task packs so that nothing is hand-maintained and everything is traceable.

## 4. The Core Workflow

1. **Create a project** (web, mobile, API, or AI; built from scratch).
2. **Define scope**: requirements (REQ) and use cases (UC) with stable IDs.
3. **Model visually**: workflows (WF), data entities (DB), sequence flows (SEQ), architecture (ARCH) — no manual Mermaid.
4. **Generate automatically**: Markdown documentation, Mermaid diagrams, and a portable Markdown workspace.
5. **Plan the roadmap**: milestones (MS) generated from requirements and dependencies.
6. **Package tasks**: the system generates agent-neutral task packs (TASK) with executable checklists (CHK), verification steps, and definitions of done.
7. **Execute with governance**: agents execute tasks; humans approve final requirements, architecture, schema, and API contracts.
8. **Verify and trace**: test cases (TC) link to requirements; traceability reports show coverage.

## 5. Major Modules

## 6. The Input Model

The system is driven by structured entities, not free-form documents:

- Project (PRJ)
- Requirement (REQ)
- Use Case (UC)
- Workflow (WF) — with start, end, and decision branches
- Data Entity / Field (DB)
- Sequence Flow (SEQ)
- Architecture Component (ARCH)
- Milestone (MS)
- Task (TASK) and Checklist (CHK)
- Approval (APR) and Decision Record (ADR)

Inputs are captured through the visual modeler and structured forms. Free-form Mermaid input is not a supported input path for end users (generation only).

## 7. The Generated Outputs

1. Markdown engineering documentation (English only, YAML frontmatter, stable IDs).
2. Mermaid diagrams: workflow, sequence, ERD, architecture — generated, never hand-written.
3. A portable Markdown workspace export (`00-meta/` … `09-agent-plans/`, `templates/`).
4. Roadmaps with milestones.
5. Agent-neutral task packs with executable checklists, verification, and definition of done.
6. Traceability and validation reports.

## 8. Agent Execution Behavior

- Task packs are **agent-neutral**: executable by Claude, ChatGPT, Qwen, or any compatible agent.
- Every task includes: ID, objective, context, constraints, input artifacts, a concrete sequential checklist, verification steps, and a definition of done.
- Agents report against the checklist; the system records completion against stable task IDs.
- Task packs never depend on a specific vendor's tooling or prompt format.

## 9. Approval and Governance Behavior

- **Automatic generation** (no approval): drafts, documentation suggestions, diagram previews, roadmap suggestions, task drafts, traceability reports, validation warnings.
- **Human approval required** for: final requirements, final architecture, final database schema, final API contracts, security-sensitive workflows, production decisions, and destructive migrations.
- Every approval is recorded (APR) with who, what, when, and why; decisions are recorded (ADR).

## 10. Hybrid Storage Behavior

- **Database is the source of truth**: SQLite holds all structured model data.
- **Markdown is generated output**: the workspace is exported from the database, regenerable at any time.
- Stable IDs are preserved in both stores so artifacts remain traceable across exports.
- No private secrets are stored in documentation or frontend code.

## 11. Product Principles

1. An internal engineering platform.
2. A full software lifecycle management system.
3. A visual spec engine.
4. A Markdown documentation generator.
5. A roadmap planner.
6. An agent task packaging system.
7. A traceability and governance system.

## 12. Mandatory Product Constraints

1. English-only generated artifacts.
2. Database as source of truth.
3. Markdown as export/output format.
4. Agent-neutral task packs.
5. Executable checklists.
6. Human approval gates plus automation.
7. No external integrations in v1.
8. Support for web, mobile, API, and AI projects.
9. Support for projects built from scratch.
10. Support for workflow, sequence, ERD, and architecture diagrams.
11. No manual Mermaid writing by the end user.

## 15. Agent Guide

If you are an agent working on SpecForge Studio:

1. Read `memory/` first (project state, decisions, constraints).
2. Read `PRD.md` and `scope.md` before touching implementation.
3. Respect the mandatory constraints in section 12; they are non-negotiable in v1.
4. Never add an external SaaS integration without explicit approval.
5. Always preserve stable IDs; never invent parallel ID systems.
6. All generated artifacts must be English, Markdown-compatible, and agent-neutral.
7. Before declaring any phase complete, check `memory/STATE.json` for the next action and update it.
